# ui
- When two sibling views share a tab/navigation bar, keep both mounted simultaneously and toggle visibility via state rather than using route-based navigation that unmounts/remounts each view. Unmounting causes unnecessary data refetches and a jarring flash/blink even when the data was already loaded moments before — the user expects instant, seamless switching with no reload. The tab bar itself must persist across all sibling views; never replace it with a standalone page that shows a page title and back button instead. Confidence: 0.95
- When assigning per-entity colors (e.g., employee chips), ensure truly unique colors rather than hash-based distribution from a limited palette, which can cause collisions. Use a deterministic method that guarantees distinct colors for each entity (e.g., index-based assignment from a larger or dynamically generated palette). Confidence: 0.70
- For date range forms with exclusion dates, offer a visual calendar picker with multi-select instead of text input. Confidence: 0.70
- Prefer inline popup editing on list items over extra UI attributes — users can tap an item to edit it. Confidence: 0.70
- Use explicit Tailwind color classes (e.g., amber-*, emerald-*) for status indicators rather than CSS variable tokens (warning, success) that may render too muted. Confidence: 0.65
- Avoid nesting content inside rounded rect containers within already-rounded cells. Use the full cell for background highlighting and separate sections with only a thin border/separator line. Confidence: 0.95
- For shift/time-based data views (both user-facing and admin review), use a weekday table grid layout instead of flat lists. Admin approval views should mirror the same table structure as the registration view, with taller cells containing chip-style entries that include actions and status inline. Confidence: 0.65
- For chip/badge elements with per-entity colors, use translucent rgba backgrounds (e.g., rgba(R,G,B,0.15)) with solid hex text colors rather than opaque/solid pastel hex backgrounds, which look too heavy. Confidence: 0.75
- Employee chip colors should be consistent across ALL views (admin and employee-facing) — when a department-based (or other entity-based) color scheme is established in one view, reuse the same color mapping in every other component that displays those entities, regardless of user role. Confidence: 0.55
- For employee-facing schedule views, assign per-employee colors (keyed by user_id) rather than per-department colors, so each individual can instantly spot their own shifts on the board. Confidence: 0.80
- When readability is the priority in dense data grids (e.g., schedule tables), prefer plain colored text labels over chip/badge containers — drop the background pill, border, and rounded corners, bump the font size, and keep only the per-entity color on the text itself. Apply this across ALL views/components that use the same pattern, not just one file. Confidence: 0.85
- For tab-switch transitions, use staggered overlapping animations: exit begins first (shorter, ~0.35s fade + slide out), entry follows after a brief delay (~0.15s) and runs longer (~0.5s slide in), creating about 0.2s of overlap where both views occupy the same space via absolute positioning. The outgoing view should exit quickly while the incoming one enters more deliberately. Avoid both fully-simultaneous starts (jarring) and fully-sequential mode="wait" (disconnected gap). Confidence: 0.80
- When switching between two sibling panels/tabs, the outgoing panel slides out toward the left and the incoming panel slides in from the right — this directionality should be reversed when switching the opposite way (outgoing slides right, incoming from left). The user expects slide direction to match the conceptual navigation direction. Confidence: 0.85
- In mobile touch interfaces, add `select-none` to read-only display text in data tables (e.g., weekday headers, labels) to prevent accidental text selection when tapping. Confidence: 0.80
- In mobile touch interfaces, avoid CSS `:hover` pseudo-class effects (e.g., `hover:bg-foreground/5`, `hover:bg-*`) on interactive buttons — they fire on any tap and create unintended flashes or stuck states. Use explicit tap handlers with brief DOM-based flash/feedback (e.g., `classList.add` + `setTimeout` removal) for touch-appropriate confirmation instead. Confidence: 0.80
- For mobile layouts, navigation tab bars should be compact single-row icon-only buttons spread evenly across the full screen width — avoid multi-line labeled chips that can consume half the viewport height. Confidence: 0.85
- Data tables must be constrained to fit within the viewport — use `max-w-full` on the container and `overflow-x-auto` (not `overflow-hidden`) so that any overflow scrolls rather than clips. When `overflow-hidden` is used for animation clipping on a parent, prefer `overflow-x-hidden` to avoid vertically cropping table content below. Confidence: 0.80
- For mobile page-level navigation (switching between sibling pages like Salary and Shift Registration), prefer a top-positioned tab bar integrated into the sticky header, replacing the page title — the tabs themselves serve as the navigation label, so a separate title is redundant. Confidence: 0.65
- Place the theme switcher inline next to the app name/logo, specifically on the login page — do NOT include it on other/app pages. Don't bury it in menus or settings. Confidence: 0.80
- For binary view-mode toggles, place the toggle as a separate button side-by-side with the adjacent header/label row (e.g., next to a week navigator), with intentional spacing to prevent accidental taps. Do NOT embed the toggle inside the label itself, and do NOT add a separate dedicated tab row — the toggle should be visually distinct but on the same row as the related control. Confidence: 0.85
- For time-period-based views (weeks, months, etc.), default to read-only/display mode for current and past periods, and to editable/action mode for future periods. Users should see their existing data first for current periods, not land on an empty registration form. Confidence: 0.80
- When the user switches to an action mode (registration, editing) that is not applicable to the currently displayed time period, auto-advance to the nearest valid future period rather than staying on the invalid period and showing an error or empty state. Confidence: 0.70
- When switching back to a read-only display view (e.g., schedule table), reset temporal context — date ranges, weeks — to the current period rather than preserving a potentially empty or stale state from prior navigation. Confidence: 0.70
- For list rows with both a row-level tap action and inline interactive child elements (e.g., checkboxes, buttons), the row itself should be the primary tappable target (use `motion.button` with `whileTap` and `onClick`), and child elements should call `e.stopPropagation()` to prevent the row action from firing. Never let child elements steal the only tap target — the row must remain tappable. Confidence: 0.75
- Display dates in Vietnamese format: `{day} Th {month}` (e.g., `3 Th 8`) rather than English `{month abbreviation} {day}` (e.g., `Aug 3`). Apply this consistently across all views that show date ranges. Confidence: 0.90
- For data tables, ensure columns displaying monetary/currency amounts have sufficient width to prevent text wrapping onto multiple lines — users expect to read amounts on a single line at a glance. This applies to allowance (PC), total, and any other numeric-amount columns. Confidence: 0.75
- Avoid verbose explanatory subtext beneath section titles or headers — keep the UI clean and minimal. If a section needs explanation, make the title itself descriptive enough rather than adding long helper text underneath. Confidence: 0.70
- For paired read/write views of adjacent time periods (e.g., a schedule table for the current week and a shift registration form for the next week), show both simultaneously rather than toggling between them: the current period as read-only display and the next period as the editable/action view. Use a single shared navigation control (e.g., week stepper) that moves both views in lockstep with a slide transition animation. Confidence: 0.85
- When a date range label inside a constrained pill/button wraps to a new line (e.g., because adding a nearby pill forces the label onto a second line), intentionally stack the start and end dates vertically: the top row shows the start date and the bottom row shows the end date, both in `dd/mm` format with no dash separator between them. De-emphasize the top row by reducing both its font size and opacity, while keeping the bottom row at normal size/opacity for visual prominence. When the full range fits on a single line, keep the full `dd/mm — dd/mm` format instead. Confidence: 0.90
